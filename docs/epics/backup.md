# Epic 10: Backup

## Status

⏳ In progress: 10.1 to 10.6 are done.

## Overview

A person opts in by connecting a private git repository, which can be a Fjord repository or anything else, on the GitHub provider for now, and sets a mode, `manual` or `auto`. Tusk commits `tusk/YYYY-mm-dd_hh-mm-ss.json` to it: the "everything" export of epic 9, the Desk and the workspaces the person owns. Connecting works as Fjord's does.

## Tasks

#### ✅ 10.1 — Credentials at rest

**Goal:** a credential can be stored so that a stolen database does not give it up.

**Design:** §21.2. **Depends on:** 1.5.

**Technical:** `src/crypto/`, as Fjord's, on the server, using Node's `crypto` only. AES-256-GCM with a random data key per credential, wrapped under the instance key; the id and purpose in the authenticated data of both layers, and the wrapping's also naming the key. `credential` table. `TUSK_ENCRYPTION_KEY` (or `_FILE`): 32 random bytes, in base64, URL-safe base64 or hex, known by a domain-separated fingerprint. Optional until something is stored. Rotation by restart with `TUSK_ENCRYPTION_KEY_PREVIOUS`, rewrapping at start-up, naming the key replaced. Stops at start-up when credentials exist and their key is absent, naming fingerprints.

**Accepts when:** a sealed value moved to another row or purpose is refused; rotation works from any replica, twice at once; a dropped key stops the server; nothing logs a secret, and each binding's test was seen to fail with it removed.

**Done as:** **`src/crypto/keys.ts`**: `parseKey` reads 32 bytes in hex, base64 or URL-safe base64 (hex first, since 64 hex characters are also valid base64 of another length) and says nothing of what was given when it is wrong; `fingerprintOf` is 16 hex characters of a SHA-256 of the key under the name `tusk:encryption-key:fingerprint:v1`, so it is not a hash of the key that anything else makes; `ringOf` is the current key and the previous. **`src/crypto/envelope.ts`**: `seal` makes a random data key for each credential, encrypts the value under it and wraps the data key under the instance key, AES-256-GCM both; the result is `t1.<fingerprint>.<wrapped key>.<payload>`. **The id and purpose are in the authenticated data of both layers and the wrapping's also names the key,** so a value moved to another row or purpose, or re-labelled with another key's fingerprint, does not open; `open` finds the key by the fingerprint the value names and wants it in the ring; `rewrap` moves only the wrapping and leaves the payload as it is. An error is a kind of failure (`malformed`, `unknown_key` naming the fingerprint, `cannot_open`) and **never a value**, and the data key is zeroed after use. **`credential` table** (`id`, `account_id`, `purpose`, `sealed`, `key_fingerprint`, times; migration `0004_credential` for both dialects) and **`src/crypto/store.ts`**, the only place that reads or writes `sealed`: `putCredential` (an upsert that holds only for the same account and purpose, and says so rather than replacing another's), `readCredential` (the account and purpose in the statement), `deleteCredential`, `deleteCredentialsOf` (for task 2.8's deletion of a person, which does not exist yet and is to call it), `keysInUse`, `assertKeys` and **`rotateCredentials`**. **At start-up** (`instrumentation-node.ts`): the settings read `TUSK_ENCRYPTION_KEY` and `_PREVIOUS` (or `_FILE`) and stop on one that is not a key, a previous key with no current one, or the same key twice, naming the setting and never its value; then `assertKeys` **stops the server when credentials are sealed under a key it was not given, naming the fingerprints**; then `rotateCredentials` moves what is wrapped under the previous key to the current, **each row by a conditional update that holds only while the row is as it was read, so that any number of replicas starting at once move each row exactly once**, and logs one line naming both keys and the count. A row that says it is under the old key and is not is left alone and does not stop the others. Tests: the keys (three forms, wrong lengths, the fingerprint's stability and that it is not a plain hash); the envelope (round trip including empty and multibyte values, differing each time, another row, purpose or key, every part tampered, malformed forms, no secret, key or binding in an error, and moving between keys with the payload untouched and the binding kept); **each of the five bindings tried on its layer alone** (the payload's id and purpose, the wrapping's id, purpose and key) and the layers not being each other's; the store on the real database (sealed in the table, owner and purpose in the statement, another account's id not replaced, a value moved to another row refused, going with the account twice over); start-up (the key dropped or another given stops it, naming the fingerprint with no key or secret in what it says; the old key beside the new moves them, says so, and is then not needed); rotation (120 credentials, twice, with no previous key, **three replicas at once moving 150 credentials exactly once each**, and a row that lies); and the settings. **Each binding was seen to fail with it removed:** with it taken out of the authenticated data, the test of its layer fails (a first version of the tests did not see the payload's, since a moved value is refused at the wrapping first, which is why each layer is tried alone). **Not run:** the same tests on sqld and PostgreSQL (Docker was not running). The conditional update is standard SQL and is held by the rotation test on each leg in CI.

#### ✅ 10.2 — The provider, and GitHub

**Goal:** the app reaches a git host through one small interface, tested against a real git repository.

**Design:** §21.2. **Depends on:** 1.2.

**Technical:** `src/providers/types.ts`: `getRepository` (including `private` and the default branch), `canWrite(ref, branch)`, `getHead`, `commit(ref, { branch, expectedHead, message, changes })`, a small part of Fjord's. Errors are ours: `unauthorized`, `forbidden`, `not_found`, `empty_repository`, `head_moved`, `too_large`, `rate_limited` (with when), `unavailable`, `invalid_request`. `src/providers/github/`: a commit is made as git makes one (blob, tree on the head's, commit, a fast-forward that is never forced); a read retried after a network failure or a 502, 503, 504; a write **never** retried; a timeout on everything; paths checked. `TUSK_GITHUB_API_URL`, https except on localhost. `src/providers/memory.ts`. `testing/contract.ts` runs against both, and `FakeGitHub`, whose storage is a real git repository; recorded answers by `scripts/record-github-fixtures.mjs`.

**Accepts when:** the contract passes on both; a moved branch gives `head_moved`, and nothing is written; a token never appears in an error, in a test that plants one.

**Done as:** **`src/providers/types.ts`**: `Provider` is four calls (`getRepository`, `canWrite`, `getHead`, `commit`; 10.3 added a fifth, `reachable`), with `RepositoryRef`, `Repository` (owner, name, `private`, default branch), `CommitRequest { branch, expectedHead, message, changes }` and `Commit { sha, paths }`. `ProviderError` carries one of the nine codes the epic names and `retryAfterMs` for `rate_limited`; **it carries no message of the host's and no value that was sent**, so there is nothing in it for a token to be in. The checks every provider makes before anything is sent are shared: `checkRepository` (owner and name as GitHub allows them), `checkBranch` (git's rules where they matter), `checkPath` (relative, no `..`, no empty or `.` segment, no `.git` segment in any case, no backslash or control character, 255 at most) and `checkCommit` (something to write, no path twice, a 40-hex `expectedHead`, no more than `MAX_COMMIT_BYTES`, 60 MB). **`src/providers/github/provider.ts`**: `GitHubProvider` over `fetch`. A commit is made as git makes one: the head is read and compared to `expectedHead` (`head_moved` and nothing sent if it is elsewhere), the files are blobs (base64, so any text is whole), a tree on the head's tree, a commit whose parent is the head, and a `PATCH` of the ref with `force: false`, so a branch that moved in the meantime is refused by the host too (a `422` that is not a fast-forward is `head_moved`). **A read is tried again** (up to `retries`, with a pause that doubles) after a network failure or a 502, 503 or 504; **a write never is**, so that an answer lost on its way is not written twice: it is `unavailable`, and the caller reads the branch to see whether it landed. Every request has a timeout (`timeoutMs`), **does not follow a redirect** (which would carry the token to another host), and is sent to an address that `checkApiUrl` accepted: https, or http on localhost, with no user, query or fragment. A `401` is `unauthorized`, a `403` that names no limit is `forbidden`, a `403` or `429` with the host's limit headers is `rate_limited` with how long (from `Retry-After`, or `X-RateLimit-Reset`), a `404` is `not_found`, a `409` is `empty_repository` (GitHub's answer for a repository with no commit), a `413` is `too_large`, a `5xx` is `unavailable`; **an answer is read for its status and its headers, never for text that goes into an error.** The token is held in a closure, so it is not a property of the provider and `String(provider)` or `JSON.stringify(provider)` does not hold it. **`src/providers/memory.ts`**: `MemoryProvider` keeps repositories with their commits, makes commit ids from what is committed (so the same history is the same ids), is fast-forward only, and checks its credential as a host does; `view({ presented, readOnly })` is the same host reached with another credential, and `failNext` and `calls` are for the tests of what a caller does when a host is unwell. **`src/providers/testing/fake-github.ts`**: `FakeGitHub`, an HTTP server on 127.0.0.1 **whose storage is a real bare git repository** driven by the `git` command (blobs by `hash-object`, trees by a throwaway index, commits by `commit-tree`, the ref by `update-ref` compare-and-swap, a fast-forward by `merge-base --is-ancestor`), so that what is tested is a commit git itself can read and `git fsck` passes. It answers as GitHub does, and can be told to fail a kind of request a number of times, to ask to be left alone, to be slow, and **to apply a write and cut the connection before the answer**. **`src/providers/testing/contract.ts`** is what every provider does the same, thirteen cases run on both (the thirteenth, `reachable`, came with 10.3) (`memory.test.ts`, `github/provider.test.ts`): the repository's facts; `not_found` and `unauthorized`; whether a credential may write (a read-only one, and an archived repository, may not); a branch's head, a branch that is not there, an empty repository; **a commit puts its files in one commit on the head and the rest of the tree is as it was**, multibyte content whole; several files and a replaced one; **`head_moved` with nothing written, and the commit going through once the head is read again with the other person's file kept**; `empty_repository`, `forbidden` and `not_found` for a commit; twelve paths and eight requests that are refused as `invalid_request` before they are sent; `too_large`; and the credential in no error. GitHub's own are tried on their own: a read tried again after two 503s and after a cut connection, and `unavailable` when it stays so; **a write whose answer is lost is sent once (one `PATCH`, one commit object), lands once, and the caller finds it by reading the head**; a write refused with a 503 is not sent again; a ref update refused as not a fast-forward is `head_moved` and the branch is where it was; `force: false` is in every ref update; `Retry-After` and the reset header give the wait; a slow host is `unavailable` at the timeout; nothing listening is `unavailable` and says nothing of the address; no redirect is followed; and **a planted token is in no error, no stack, no string or enumeration of the provider, and only in the `Authorization` header of a request**. **Each rule was seen to fail with it broken:** with the head comparison taken out, with `force: true`, with writes retried, and with redirects followed, the test of it fails (a first look at retried writes was a crude change, and a second, a real retry loop around the write, fails three tests). **`TUSK_GITHUB_API_URL`** is a setting (`Config.githubApiUrl`, default `https://api.github.com`, `.env.example` and `deploy/.env.example`): the server stops at start-up on one that is not https or localhost, naming the setting and not the address. **Left out:** `scripts/record-github-fixtures.mjs` and recorded answers: they need a real token and a repository to record from, and the fake already answers as GitHub's documentation says; the day a real answer differs, it is recorded and added to the fake. The code that uses a provider (`runBackup`, the connection) is 10.3 and 10.4. **Not run:** nothing here touches the database, so there are no other legs; the fake needs the `git` command, which CI's runners and the dev machine have.

#### ✅ 10.3 — Connecting with a token

**Goal:** connect a repository with a fine-grained token, with mistakes explained.

**Design:** §21.2, §21.5, §23.3. **Depends on:** 2.7, 10.1, 10.2.

**Technical:** `backup_connection`, one per account. `src/backup/connection.ts`: parses an address (`https://github.com/o/r`, with or without `.git`, `git@github.com:o/r`, `o/r`), refusing another host or a password in it. Checked in order: token accepted; repository visible; **private**; default branch has something in it (else "add a README first"); `canWrite`. Each refusal is a message of ours. A token that fails leaves nothing behind. A token reaching more than it needs is accepted with a warning naming how many others it can reach. `POST`/`DELETE /api/backup/connection`, with `Origin` checked. The token is in one request and no response. A Backup section in Settings > Data, saying plainly what will be sent and where. Disconnect deletes the connection and credential. Without a key, the section says why not. `People` (2.8) deletes both; the deletion screen says the repository is left alone.

**Accepts when:** each refusal has a test against `FakeGitHub`, on all three databases; a public repository cannot be connected; another account's connection is a 404; the token reaches no response, log or error.

**Done as:** **`backup_connection`** (migration `0005_backup_connection` for both dialects): `account_id` is the key, so an account has one; `kind` (`token`), `repository` (`owner/name`), `branch` (the default branch it was found to have), `credential_id` and `created_at`. The columns for the backups themselves (mode, times, failures) are added by 10.4 to 10.6, as the schema's convention is. **`src/backup/address.ts`**: `parseAddress` takes `https://github.com/o/r` (with or without `.git`, a trailing slash, `www.`), `git@github.com:o/r` and `o/r`, and refuses, with the reason: **a password or user name in the address (`password`, looked at before the host)**, another host (`host`), `http`, a query or fragment, a path of more or fewer than two parts, an owner or name GitHub does not allow, and anything over 300 characters (`address`). The hosts allowed are `github.com`, or the Enterprise Server `TUSK_GITHUB_API_URL` names and then no other, GitHub included. **`src/backup/connection.ts`**: `connectRepository` checks, in this order and before anything is written: the address; that the server has a key (`no_key`); that the token is a token (8 to 512 printable characters with no space, so that nothing else is sent to a host as a header); the host accepts it (`token_rejected`); it can see the repository (`not_visible`, for both a 404 and a 403); **the repository is private (`public`)**; its default branch has something in it (`empty`: "add a file first"); and the token can write (`read_only`, which an archived repository is too). A failure of the host is `rate_limited` or `unreachable`. **Each is a sentence of ours (`PROBLEM_MESSAGES`) that says what to do; none carries GitHub's text, the address or the token,** and a refusal is tested to leave no connection and no credential. A token that reaches more than this repository is accepted, and the result says how many others (`alsoReaches`); the provider gained a fifth call for it, `reachable()` (GitHub's `GET /user/repos`, a hundred at most; counting it failing is not a reason to refuse). The token is then sealed by `putCredential` under the id `backup:<account>`, **so that one account has one credential and connecting again replaces it**, and the row is written by an upsert; if the row fails, the credential just sealed is removed again. **A refused try does not disconnect the connection that works.** `disconnectRepository` deletes the row and the credential, leaves the repository alone, and is safe to run twice. **`src/backup/endpoint.ts`** and `app/api/backup/connection/route.ts`: `GET` (whether this server can keep a token, and the connection: repository, a link to it, branch, kind and when, **not even the credential's id**), `POST { repository, token }` (200 with the connection and, when the token reaches more, a warning in words; 422 with `{ code, message }`; 400 for what is not a request; 413 over 4 KB; 429 after ten tries a minute, each being a call to GitHub with a token a person typed) and `DELETE` (204, or 404 when this account has nothing connected). The route is wrapped in `accountRoute` and listed in `routes.ts`; the connection is found by the session's account and by nothing in the request, so there is no other account's to ask for, and **another account's `DELETE` is the 404 of nothing, with the first account's connection where it was**. **`BackupSection`** in Settings > Data says what will be sent and where before it asks for anything (plain text, on GitHub's servers, a private repository only, checked each time, disconnecting leaves the repository alone), how to make a fine-grained token for one repository with _Contents: Read and write_, and takes the address and the token in a password field that is cleared once sent; without a key it says why connecting is not offered. Tests: the address (the forms taken, twenty that are refused with the reason, an Enterprise Server); the connection on the real database and `FakeGitHub` (every refusal and its order, nothing left behind, a token made for another repository, public made private and back, a token that reaches more and one that reaches one, replacing, two accounts apart, disconnecting twice and the repository untouched, the token sealed and in no row or result); the endpoint with two real accounts (who may call it and `Origin`, no secret in any body or header, every refusal's status, 404 for what is not theirs, bad requests, the rate); and a browser test in Chromium and WebKit (a public repository refused in words, another host refused, connected, the token not in the page, still connected after a reload, disconnected, and nothing written to the repository). The e2e instance now has an instance key and a GitHub address on this machine (`playwright.config.ts`). **Each rule was seen to fail with it broken:** the private check, the write check, the empty check, the password rule, the host rule, the credential's id in a response, and the disconnect's account. **Left out:** `People` deleting the connection and credential (2.8 does not exist; `deleteCredentialsOf` is there for it, and it is to delete the `backup_connection` row too, and its deletion screen is to say the repository is left alone); a Backup section's last and next backup (10.4 and 10.5). **Not run:** the same tests on sqld and PostgreSQL (Docker was not running); the upsert and the deletes are standard SQL, and CI runs them on each.

#### ✅ 10.4 — Making a backup

**Goal:** Back up now puts a file in the repository.

**Design:** §21.3. **Depends on:** 9.1, 10.3, 13.2.

**Technical:** `src/backup/run.ts`: `runBackup(accountId, now, trigger)`. Read the connection; read the token; `getRepository`, stopping if it has become public; read the rows in a short transaction, closed before any call, and build §20's "everything" shape on the server: the Desk and every workspace the person owns (a personal-key Desk's part is ciphertext: 14.5); refuse over 50 MB; path `tusk/${YYYY-mm-dd_hh-mm-ss}.json` in UTC, from a pure `backupPath(now)`; `commit` on the head read, message `Tusk backup 2026-11-06 14:30:00 UTC`. On `head_moved`, read and try once more. Record `last_backup_at`, `last_backup_path` and `last_fingerprint` on confirmed success. **Back up now:** `POST /api/backup/run`, limited to once a minute through `rate_bucket`, always commits, and shows a link to the file. Other files in the repository are never touched.

**Accepts when:** against `FakeGitHub`, a file appears at the right path with the export's bytes, in a real commit, on the default branch, with the rest of the tree unchanged; the file imports through 9.2; a commit into a repository with `fjord.json` leaves `fjord verify` content; a moved head succeeds; no transaction is open during a call.

**Done as:** **`src/backup/path.ts`**, pure: `backupPath(now)` is `tusk/YYYY-mm-dd_hh-mm-ss.json` in UTC (tested against a machine in another zone, padding, the year's edge and that the names sort as the times do), `backupMessage(now)` is `Tusk backup 2026-11-06 14:30:00 UTC`, and **`backupFingerprint(seq, stamps)`** is a SHA-256 (32 hex characters) of the Desk's `seq` and a stamp for each thing of the workspaces the person owns, in any order. **The stamps are more than the epic's "`updated_at` of each workspace":** `ownedStamps` in `src/workspaces/export.ts` reads the workspace's time, each board's `version` (which every operation on the board moves; the workspace's own time does not move when a card does) and archiving, and each person with their role, because a fingerprint that missed a change would lose it, and one that changed too often only costs a spare file. **`src/backup/snapshot.ts`**: `takeSnapshot` reads, **in one short transaction that is over before the host is called again,** the Desk by pulling from zero with `pull` (which never skips a row) into the same `buildDesk` the browser uses, the owned workspaces with `exportOwned`, and the stamps, and makes the "everything" file of §20 and the fingerprint; a personal-key Desk's ciphertext (14.5) is not yet there, since no Desk has a personal key. **`src/backup/run.ts`**: `runBackup(deps, accountId, now, trigger)` reads the connection; opens the token (one that cannot be opened is `token_rejected`, and no error from the crypto is kept); asks for the repository **again and stops if it has become public** (`public`, with nothing written); takes the snapshot; refuses a file over 50 MB (`too_large`); reads the default branch's head and commits the file with `expectedHead` set to it (never forced); **on `head_moved` reads the head again and tries once more, and no more** (a test counts two attempts); and records `last_backup_at`, `last_backup_path` and `last_fingerprint` (migration `0006_backup_record`, for both dialects) **only once the host has confirmed the commit.** Every failure is a kind (`not_connected`, `no_key`, `token_rejected`, `not_visible`, `public`, `read_only`, `empty`, `too_large`, `head_moved`, `rate_limited` with when, `unreachable`) with a sentence of ours (`RUN_MESSAGES`), never the host's words. **A write whose answer is lost is sent once, is `unreachable`, records nothing, and may have landed:** the next backup is another file, so the worst case is one too many. Failures are returned and not kept: keeping them and what they stop are 10.6's, and `trigger` (`manual` or `auto`) is carried for 10.5. **`POST /api/backup/run`** (`runNow`, listed in `routes.ts`, `accountRoute`): 404 when nothing is connected for the account, 429 beyond once a minute (counted in `rate_bucket`, a refused count still counting), 422 with `{ code, message }`, or 200 with where the file is; `GET /api/backup/connection` now also gives the last backup and a link to its file. The Backup section has **Back up now** and shows the last backup as a link. Tests: the pure functions; against `FakeGitHub` and the real database, the file at the right path **with exactly the export's bytes** in a real commit that `git fsck` passes, on the default branch, with every other file of the tree (a `fjord.json` among them) byte for byte as it was; the file passing `validateFile` with the Desk in it; the owned workspaces in and a member's own not; the record, once confirmed; two runs making two files and nothing rewritten; the fingerprint stable until something changes; **a moved head read again and succeeding** (the other person's file kept); a head that moves twice giving up with nothing written; a repository made public getting no write; the lost answer sent once, recorded as nothing and the file there once; each kind of failure; no key and no connection; a token sealed under another key; **no transaction open during a call to the host** (a write from inside each call, which on a file would wait forever behind an open transaction in this process); and the token in no result; the endpoint with two real accounts (who may call it, the 404, the file, the minute, the 422 with no secret); and a browser test in Chromium and WebKit (a backup, its link, the file in the repository, and "once a minute"; WebKit waits out the limit the first browser used, because they share one account). **Each rule was seen to fail with it broken:** the public check, the retry count (which the first version of the test did not see, since a branch that always moves fails anyway: it now counts attempts), retrying on anything but `head_moved`, a local-time path, and a fingerprint that leaves a stamp out. **Left out:** "the file imports through 9.2" is shown by `validateFile` and `summarise` reading it, not by importing it into a database; `fjord verify` itself (Fjord's tool) is not run, the tree being byte for byte as it was. **Not run:** the same tests on sqld and PostgreSQL (Docker was not running); the transaction test is only strict on a file.

#### ✅ 10.5 — Modes, and the auto job

**Goal:** `auto` runs on its frequency, and commits only when something changed.

**Design:** §21.1, §21.4. **Depends on:** 1.6, 10.4.

**Technical:** `mode` (`manual`, `auto`), `frequency` (`hourly`, `6h`, `daily`, `weekly`; default `daily`), `next_backup_at`. A control in the section, showing the last and next backup. A job per minute: selects due connections, capped per tick, claims each by a conditional update moving `next_backup_at` on, and runs them with small concurrency. An auto run compares a fingerprint first, `backupFingerprint(seq, workspaces)`, pure, from the Desk's `seq` and the `updated_at` of each workspace the person owns: equal to `last_fingerprint` means no commit, only a record of when it looked. A switch to `manual` clears the next. `next_backup_at` is pure: `nextBackup(frequency, now)`, with a little spread so that a server's connections do not all fall on the same minute.

**Accepts when:** two runners make one commit; a quiet account's daily run makes no commit, and a change makes one the next day; `manual` is never run by the job; times are tested with the clock passed in.

**Done as:** **`backup_connection`** gained `mode` (`manual`, the default, or `auto`), `frequency` (`hourly`, `6h`, `daily` by default, `weekly`), `next_backup_at`, `last_checked_at` (when an automatic run last looked, whether it wrote or found nothing changed) and an index on the due time (migration `0007_backup_schedule` for both dialects). **`src/backup/schedule.ts`**, pure with the clock passed in: `nextBackup(frequency, now, accountId, due?)` is one interval from `now` plus the account's spread when a mode or frequency is chosen, and after a run is **`due` plus one interval, so that the schedule keeps its place and does not drift by how late the job ran or how long the run took** (a connection missed by more than an interval starts over from `now`, and no time it returns is in the past); `spreadMs` is a fixed amount per account from a hash of its id, up to a tenth of the interval and never over ten minutes, so that a server's connections do not fall on one minute. **`src/backup/auto.ts`**: `setSchedule` (`manual` clears the next time; `auto`, or another frequency while on it, sets it; changing nothing leaves it where it was; a frequency chosen while on `manual` is kept for when `auto` is chosen) and **`runDueBackups(deps, now, { cap, concurrency })`**, the job's work with the clock passed in: it takes the `auto` connections whose time has come, oldest first, at most 20 a tick, **claims each by a conditional update that moves `next_backup_at` on and holds only while it is still what was read** (`claim`), and only the process that won runs it, three at a time; a failure is counted, logged by its kind alone, and **the connection has already been moved on, so it is tried again at its next time and never at once**. `runBackup` with the `auto` trigger **compares the fingerprint with the last backup's and writes nothing when they are equal**, recording only `last_checked_at` (a back up now always writes); connecting to another repository clears what is known of the last backup, so that the new one gets a first backup. **The job `backups`** (`src/jobs/index.ts`) runs `runDueBackups` every minute and logs one line when it took any; it does nothing on a server with no key. `PATCH /api/backup/connection { mode?, frequency? }` (400 for anything else, 404 where nothing is connected, listed in `routes.ts`), and `GET` gives the mode, frequency, next time and last checked. The Backup section has a control for how backups are made, a choice of frequency when automatic, and the last checked and next times. Tests: the pure functions (the spread's bounds and stability and that it varies; the grid kept after a late run; the missed interval; never a time in the past); the choice (`setSchedule` in every direction); **the job with the clock passed in**: a connection run when due and not before and keeping its place; **a `manual` connection with a due time written into it never run**; **three runners at the same time making one commit**; a quiet account looked at with no write call at all and a change written the next time; the cap and the order; a failure moved on and not tried again a minute later, and the others unaffected; no key; a new repository getting a first backup; and the endpoint with two real accounts; and the browser test in both browsers (choosing automatic, how often, kept after a reload, back to manual). **Each rule was seen to fail with it broken:** the claim being required to win, the claim's check of the time it read, switching to manual clearing the time, the fingerprint comparison (both its existence and its being only for `auto`), the grid, clearing the record on a new connection, and the next time after a run; the `mode = 'auto'` check in the job's query and in the claim are two layers of one guard, and a test fails only with both removed. **Left out:** nothing stops `auto` on a failure yet, and a failed run is not shown (10.6); a run is counted in the log line and not kept. **Not run:** the same tests on sqld and PostgreSQL (Docker was not running); the claim is a standard conditional update, and the three-runners test on each is CI's.

#### ✅ 10.6 — Failures

**Goal:** a backup that fails says so, and never spins against GitHub.

**Design:** §21.4. **Depends on:** 8.1, 10.5.

**Technical:** `failure_kind`, `failures`, `stopped_at`. A network failure, `unavailable` or `rate_limited`: retried at the next due time, or when GitHub says. `unauthorized`, `forbidden`, `not_found`, a repository made public: **stops auto**, sets `stopped_at`, and adds a notice to the Inbox (8.1) once. Settings always shows it, with what to do; a repaired token or **Back up now** resumes. A lost answer is `unavailable`, is never retried in the run, and leaves `last_fingerprint` alone, so the worst case is one file too many.

**Accepts when:** each kind has a test; a stopped connection makes no calls on later ticks; a revoked token is reported in words, with none of GitHub's text and no token; a lost answer doesn't record success.

**Done as:** **`backup_connection`** gained `failure_kind`, `failures` (in a row) and `stopped_at` (migration `0010_backup_failures`). **`src/backup/failure.ts`**: `runBackup` now keeps what came of every run. **A failure that will mend itself** (`unreachable`, which a lost answer is, `rate_limited`, `head_moved`, `moving`) is counted and **tried again at the next due time, never at once**; a host that said when to come back moves the next automatic backup to then if that is later (three hours is three hours, not the hourly time). **A failure that will not stops the automatic backups** (`STOPS`: a token that no longer works, one that can no longer write, a repository gone, made public or empty, a file too big, a key not confirmed, a server that lost its key; a test holds that every kind there is is one or the other, so a new kind has to be decided): `stopped_at` is set **by a conditional update that only one caller wins, and the winner writes the Inbox notice in the same transaction, so the person is told once** however many fail at the same moment and however often after. The notice is a new kind, `backup_stopped` (from the app, with no actor and no workspace; a person can turn it off in Settings > Notifications, and then it is not written though the stop stands), and says in words why and where to go ("Automatic backups have stopped: the repository has been made public. Open Settings, Data, to see what to do."), linking to Settings > Data. **A stopped connection is not claimed by the job**, in its query and in the claim: it makes no calls at all on later ticks (a test counts the requests). Settings > Data always shows the failure, in our words, as a warning while it will try again and as an error once stopped, with what to do. **What resumes it:** Back up now (a success clears the failures and the stop), connecting again (a repaired token), choosing automatic again, and confirming the key when that was the failure; **an automatic run that finds nothing changed is a success too**. A lost answer records no success and repeats nothing (it is `unreachable`, `last_fingerprint` untouched). Tests: the classification; failures counted in a row; the stop and the one notice (three failing at once and then again); a person who turned the kind off; the notice's words for every stopping kind and its link; **a revoked token stops the connection, says so in words with none of GitHub's text and no token (a body of "HOST TEXT" and a planted token are in nothing a person reads), and later ticks make no request**; resumed by Back up now, by connecting again and by choosing automatic again; a failure that mends itself tried at the next time and not a minute later and then working; the wait GitHub asked for; the lost answer; one account's failure not another's; and confirming the key. **Each rule was seen to fail with it broken:** the one notice, the kinds that stop, the clearing on a success, on connecting and on choosing automatic, and the wait GitHub asked for; the stopped check in the job's query and the one in its claim each cover for the other, so a test fails only with both removed. **Not run:** the same tests on sqld and PostgreSQL (Docker was not running).

#### 📋 10.7 — Connecting through the GitHub App

**Goal:** connect without handling a token, where the operator has set it up.

**Design:** §21.2. **Depends on:** 10.6.

**Technical:** `TUSK_GITHUB_APP_*`, all or none. **Install on GitHub**, choosing one repository; on return, `state` checked against an `HttpOnly`, `SameSite=Lax` cookie, and the `code` traded for the person's token, used once to ask which repositories of that installation they can reach. No token kept: the credential store holds which installation; `InstallationTokens` signs a JWT (RS256, nine minutes) for an hour's token, kept in memory until five minutes before it expires. `POST /api/webhooks/github`, by signature alone, constant time, over exact bytes, capped: `installation` and `installation_repositories` disconnect what the App lost. The checks of 10.3 apply. `deploy/README.md` says how to register it.

**Accepts when:** the `state` check and the person's-own-repositories check each have a test seen to fail with them off; a removed installation disconnects; a token connection continues to work beside it. Real GitHub is checked by hand once, and the epic says so.
