# Epic 10: Backup

## Status

⏳ In progress: 10.1 and 10.2 are done.

## Overview

A person opts in by connecting a private git repository, which can be a Fjord repository or anything else, on the GitHub provider for now, and sets a mode, `manual` or `auto`. Tusk commits `tusk/YYYY-mm-dd_hh-mm-ss.json` to it: the "everything" export of epic 9, the Desk and the workspaces the person owns. Connecting works as Fjord's does.

## Tasks

#### ✅ 10.1 — Credentials at rest

**Goal:** a credential can be stored so that a stolen database does not give it up.

**Design:** §21.2. **Depends on:** 1.5.

**Technical:** `src/crypto/`, as Fjord's, on the server, using Node's `crypto` only. AES-256-GCM with a random data key per credential, wrapped under the instance key; the id and purpose in the authenticated data of both layers, and the wrapping's also naming the key. `credential` table. `TUSK_ENCRYPTION_KEY` (or `_FILE`): 32 random bytes, in base64, URL-safe base64 or hex, known by a domain-separated fingerprint. Optional until something is stored. Rotation by restart with `TUSK_ENCRYPTION_KEY_PREVIOUS`, rewrapping at start-up, naming the key replaced. Stops at start-up when credentials exist and their key is absent, naming fingerprints.

**Accepts when:** a sealed value moved to another row or purpose is refused; rotation works from any replica, twice at once; a dropped key stops the server; nothing logs a secret, and each binding's test was seen to fail with it removed.

**Done as:** **`src/crypto/keys.ts`**: `parseKey` reads 32 bytes in hex, base64 or URL-safe base64 (hex first, since 64 hex characters are also valid base64 of another length) and says nothing of what was given when it is wrong; `fingerprintOf` is 16 hex characters of a SHA-256 of the key under the name `tusk:encryption-key:fingerprint:v1`, so it is not a hash of the key that anything else makes; `ringOf` is the current key and the previous. **`src/crypto/envelope.ts`**: `seal` makes a random data key for each credential, encrypts the value under it and wraps the data key under the instance key, AES-256-GCM both; the result is `t1.<fingerprint>.<wrapped key>.<payload>`. **The id and purpose are in the authenticated data of both layers and the wrapping's also names the key,** so a value moved to another row or purpose, or re-labelled with another key's fingerprint, does not open; `open` finds the key by the fingerprint the value names and wants it in the ring; `rewrap` moves only the wrapping and leaves the payload as it is. An error is a kind of failure (`malformed`, `unknown_key` naming the fingerprint, `cannot_open`) and **never a value**, and the data key is zeroed after use. **`credential` table** (`id`, `account_id`, `purpose`, `sealed`, `key_fingerprint`, times; migration `0004_credential` for both dialects) and **`src/crypto/store.ts`**, the only place that reads or writes `sealed`: `putCredential` (an upsert that holds only for the same account and purpose, and says so rather than replacing another's), `readCredential` (the account and purpose in the statement), `deleteCredential`, `deleteCredentialsOf` (for task 2.8's deletion of a person, which does not exist yet and is to call it), `keysInUse`, `assertKeys` and **`rotateCredentials`**. **At start-up** (`instrumentation-node.ts`): the settings read `TUSK_ENCRYPTION_KEY` and `_PREVIOUS` (or `_FILE`) and stop on one that is not a key, a previous key with no current one, or the same key twice, naming the setting and never its value; then `assertKeys` **stops the server when credentials are sealed under a key it was not given, naming the fingerprints**; then `rotateCredentials` moves what is wrapped under the previous key to the current, **each row by a conditional update that holds only while the row is as it was read, so that any number of replicas starting at once move each row exactly once**, and logs one line naming both keys and the count. A row that says it is under the old key and is not is left alone and does not stop the others. Tests: the keys (three forms, wrong lengths, the fingerprint's stability and that it is not a plain hash); the envelope (round trip including empty and multibyte values, differing each time, another row, purpose or key, every part tampered, malformed forms, no secret, key or binding in an error, and moving between keys with the payload untouched and the binding kept); **each of the five bindings tried on its layer alone** (the payload's id and purpose, the wrapping's id, purpose and key) and the layers not being each other's; the store on the real database (sealed in the table, owner and purpose in the statement, another account's id not replaced, a value moved to another row refused, going with the account twice over); start-up (the key dropped or another given stops it, naming the fingerprint with no key or secret in what it says; the old key beside the new moves them, says so, and is then not needed); rotation (120 credentials, twice, with no previous key, **three replicas at once moving 150 credentials exactly once each**, and a row that lies); and the settings. **Each binding was seen to fail with it removed:** with it taken out of the authenticated data, the test of its layer fails (a first version of the tests did not see the payload's, since a moved value is refused at the wrapping first, which is why each layer is tried alone). **Not run:** the same tests on sqld and PostgreSQL (Docker was not running). The conditional update is standard SQL and is held by the rotation test on each leg in CI.

#### ✅ 10.2 — The provider, and GitHub

**Goal:** the app reaches a git host through one small interface, tested against a real git repository.

**Design:** §21.2. **Depends on:** 1.2.

**Technical:** `src/providers/types.ts`: `getRepository` (including `private` and the default branch), `canWrite(ref, branch)`, `getHead`, `commit(ref, { branch, expectedHead, message, changes })`, a small part of Fjord's. Errors are ours: `unauthorized`, `forbidden`, `not_found`, `empty_repository`, `head_moved`, `too_large`, `rate_limited` (with when), `unavailable`, `invalid_request`. `src/providers/github/`: a commit is made as git makes one (blob, tree on the head's, commit, a fast-forward that is never forced); a read retried after a network failure or a 502, 503, 504; a write **never** retried; a timeout on everything; paths checked. `TUSK_GITHUB_API_URL`, https except on localhost. `src/providers/memory.ts`. `testing/contract.ts` runs against both, and `FakeGitHub`, whose storage is a real git repository; recorded answers by `scripts/record-github-fixtures.mjs`.

**Accepts when:** the contract passes on both; a moved branch gives `head_moved`, and nothing is written; a token never appears in an error, in a test that plants one.

**Done as:** **`src/providers/types.ts`**: `Provider` is four calls (`getRepository`, `canWrite`, `getHead`, `commit`), with `RepositoryRef`, `Repository` (owner, name, `private`, default branch), `CommitRequest { branch, expectedHead, message, changes }` and `Commit { sha, paths }`. `ProviderError` carries one of the nine codes the epic names and `retryAfterMs` for `rate_limited`; **it carries no message of the host's and no value that was sent**, so there is nothing in it for a token to be in. The checks every provider makes before anything is sent are shared: `checkRepository` (owner and name as GitHub allows them), `checkBranch` (git's rules where they matter), `checkPath` (relative, no `..`, no empty or `.` segment, no `.git` segment in any case, no backslash or control character, 255 at most) and `checkCommit` (something to write, no path twice, a 40-hex `expectedHead`, no more than `MAX_COMMIT_BYTES`, 60 MB). **`src/providers/github/provider.ts`**: `GitHubProvider` over `fetch`. A commit is made as git makes one: the head is read and compared to `expectedHead` (`head_moved` and nothing sent if it is elsewhere), the files are blobs (base64, so any text is whole), a tree on the head's tree, a commit whose parent is the head, and a `PATCH` of the ref with `force: false`, so a branch that moved in the meantime is refused by the host too (a `422` that is not a fast-forward is `head_moved`). **A read is tried again** (up to `retries`, with a pause that doubles) after a network failure or a 502, 503 or 504; **a write never is**, so that an answer lost on its way is not written twice: it is `unavailable`, and the caller reads the branch to see whether it landed. Every request has a timeout (`timeoutMs`), **does not follow a redirect** (which would carry the token to another host), and is sent to an address that `checkApiUrl` accepted: https, or http on localhost, with no user, query or fragment. A `401` is `unauthorized`, a `403` that names no limit is `forbidden`, a `403` or `429` with the host's limit headers is `rate_limited` with how long (from `Retry-After`, or `X-RateLimit-Reset`), a `404` is `not_found`, a `409` is `empty_repository` (GitHub's answer for a repository with no commit), a `413` is `too_large`, a `5xx` is `unavailable`; **an answer is read for its status and its headers, never for text that goes into an error.** The token is held in a closure, so it is not a property of the provider and `String(provider)` or `JSON.stringify(provider)` does not hold it. **`src/providers/memory.ts`**: `MemoryProvider` keeps repositories with their commits, makes commit ids from what is committed (so the same history is the same ids), is fast-forward only, and checks its credential as a host does; `view({ presented, readOnly })` is the same host reached with another credential, and `failNext` and `calls` are for the tests of what a caller does when a host is unwell. **`src/providers/testing/fake-github.ts`**: `FakeGitHub`, an HTTP server on 127.0.0.1 **whose storage is a real bare git repository** driven by the `git` command (blobs by `hash-object`, trees by a throwaway index, commits by `commit-tree`, the ref by `update-ref` compare-and-swap, a fast-forward by `merge-base --is-ancestor`), so that what is tested is a commit git itself can read and `git fsck` passes. It answers as GitHub does, and can be told to fail a kind of request a number of times, to ask to be left alone, to be slow, and **to apply a write and cut the connection before the answer**. **`src/providers/testing/contract.ts`** is what every provider does the same, twelve cases run on both (`memory.test.ts`, `github/provider.test.ts`): the repository's facts; `not_found` and `unauthorized`; whether a credential may write (a read-only one, and an archived repository, may not); a branch's head, a branch that is not there, an empty repository; **a commit puts its files in one commit on the head and the rest of the tree is as it was**, multibyte content whole; several files and a replaced one; **`head_moved` with nothing written, and the commit going through once the head is read again with the other person's file kept**; `empty_repository`, `forbidden` and `not_found` for a commit; twelve paths and eight requests that are refused as `invalid_request` before they are sent; `too_large`; and the credential in no error. GitHub's own are tried on their own: a read tried again after two 503s and after a cut connection, and `unavailable` when it stays so; **a write whose answer is lost is sent once (one `PATCH`, one commit object), lands once, and the caller finds it by reading the head**; a write refused with a 503 is not sent again; a ref update refused as not a fast-forward is `head_moved` and the branch is where it was; `force: false` is in every ref update; `Retry-After` and the reset header give the wait; a slow host is `unavailable` at the timeout; nothing listening is `unavailable` and says nothing of the address; no redirect is followed; and **a planted token is in no error, no stack, no string or enumeration of the provider, and only in the `Authorization` header of a request**. **Each rule was seen to fail with it broken:** with the head comparison taken out, with `force: true`, with writes retried, and with redirects followed, the test of it fails (a first look at retried writes was a crude change, and a second, a real retry loop around the write, fails three tests). **`TUSK_GITHUB_API_URL`** is a setting (`Config.githubApiUrl`, default `https://api.github.com`, `.env.example` and `deploy/.env.example`): the server stops at start-up on one that is not https or localhost, naming the setting and not the address. **Left out:** `scripts/record-github-fixtures.mjs` and recorded answers: they need a real token and a repository to record from, and the fake already answers as GitHub's documentation says; the day a real answer differs, it is recorded and added to the fake. The code that uses a provider (`runBackup`, the connection) is 10.3 and 10.4. **Not run:** nothing here touches the database, so there are no other legs; the fake needs the `git` command, which CI's runners and the dev machine have.

#### 📋 10.3 — Connecting with a token

**Goal:** connect a repository with a fine-grained token, with mistakes explained.

**Design:** §21.2, §21.5, §23.3. **Depends on:** 2.7, 10.1, 10.2.

**Technical:** `backup_connection`, one per account. `src/backup/connection.ts`: parses an address (`https://github.com/o/r`, with or without `.git`, `git@github.com:o/r`, `o/r`), refusing another host or a password in it. Checked in order: token accepted; repository visible; **private**; default branch has something in it (else "add a README first"); `canWrite`. Each refusal is a message of ours. A token that fails leaves nothing behind. A token reaching more than it needs is accepted with a warning naming how many others it can reach. `POST`/`DELETE /api/backup/connection`, with `Origin` checked. The token is in one request and no response. A Backup section in Settings > Data, saying plainly what will be sent and where. Disconnect deletes the connection and credential. Without a key, the section says why not. `People` (2.8) deletes both; the deletion screen says the repository is left alone.

**Accepts when:** each refusal has a test against `FakeGitHub`, on all three databases; a public repository cannot be connected; another account's connection is a 404; the token reaches no response, log or error.

#### 📋 10.4 — Making a backup

**Goal:** Back up now puts a file in the repository.

**Design:** §21.3. **Depends on:** 9.1, 10.3, 13.2.

**Technical:** `src/backup/run.ts`: `runBackup(accountId, now, trigger)`. Read the connection; read the token; `getRepository`, stopping if it has become public; read the rows in a short transaction, closed before any call, and build §20's "everything" shape on the server: the Desk and every workspace the person owns (a personal-key Desk's part is ciphertext: 14.5); refuse over 50 MB; path `tusk/${YYYY-mm-dd_hh-mm-ss}.json` in UTC, from a pure `backupPath(now)`; `commit` on the head read, message `Tusk backup 2026-11-06 14:30:00 UTC`. On `head_moved`, read and try once more. Record `last_backup_at`, `last_backup_path` and `last_fingerprint` on confirmed success. **Back up now:** `POST /api/backup/run`, limited to once a minute through `rate_bucket`, always commits, and shows a link to the file. Other files in the repository are never touched.

**Accepts when:** against `FakeGitHub`, a file appears at the right path with the export's bytes, in a real commit, on the default branch, with the rest of the tree unchanged; the file imports through 9.2; a commit into a repository with `fjord.json` leaves `fjord verify` content; a moved head succeeds; no transaction is open during a call.

#### 📋 10.5 — Modes, and the auto job

**Goal:** `auto` runs on its frequency, and commits only when something changed.

**Design:** §21.1, §21.4. **Depends on:** 1.6, 10.4.

**Technical:** `mode` (`manual`, `auto`), `frequency` (`hourly`, `6h`, `daily`, `weekly`; default `daily`), `next_backup_at`. A control in the section, showing the last and next backup. A job per minute: selects due connections, capped per tick, claims each by a conditional update moving `next_backup_at` on, and runs them with small concurrency. An auto run compares a fingerprint first, `backupFingerprint(seq, workspaces)`, pure, from the Desk's `seq` and the `updated_at` of each workspace the person owns: equal to `last_fingerprint` means no commit, only a record of when it looked. A switch to `manual` clears the next. `next_backup_at` is pure: `nextBackup(frequency, now)`, with a little spread so that a server's connections do not all fall on the same minute.

**Accepts when:** two runners make one commit; a quiet account's daily run makes no commit, and a change makes one the next day; `manual` is never run by the job; times are tested with the clock passed in.

#### 📋 10.6 — Failures

**Goal:** a backup that fails says so, and never spins against GitHub.

**Design:** §21.4. **Depends on:** 8.1, 10.5.

**Technical:** `failure_kind`, `failures`, `stopped_at`. A network failure, `unavailable` or `rate_limited`: retried at the next due time, or when GitHub says. `unauthorized`, `forbidden`, `not_found`, a repository made public: **stops auto**, sets `stopped_at`, and adds a notice to the Inbox (8.1) once. Settings always shows it, with what to do; a repaired token or **Back up now** resumes. A lost answer is `unavailable`, is never retried in the run, and leaves `last_fingerprint` alone, so the worst case is one file too many.

**Accepts when:** each kind has a test; a stopped connection makes no calls on later ticks; a revoked token is reported in words, with none of GitHub's text and no token; a lost answer doesn't record success.

#### 📋 10.7 — Connecting through the GitHub App

**Goal:** connect without handling a token, where the operator has set it up.

**Design:** §21.2. **Depends on:** 10.6.

**Technical:** `TUSK_GITHUB_APP_*`, all or none. **Install on GitHub**, choosing one repository; on return, `state` checked against an `HttpOnly`, `SameSite=Lax` cookie, and the `code` traded for the person's token, used once to ask which repositories of that installation they can reach. No token kept: the credential store holds which installation; `InstallationTokens` signs a JWT (RS256, nine minutes) for an hour's token, kept in memory until five minutes before it expires. `POST /api/webhooks/github`, by signature alone, constant time, over exact bytes, capped: `installation` and `installation_repositories` disconnect what the App lost. The checks of 10.3 apply. `deploy/README.md` says how to register it.

**Accepts when:** the `state` check and the person's-own-repositories check each have a test seen to fail with them off; a removed installation disconnects; a token connection continues to work beside it. Real GitHub is checked by hand once, and the epic says so.
